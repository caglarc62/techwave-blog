Git ve GitHub Başlangıç Rehberi: Sıfırdan Versiyon Kontrol

📅 10 Kasım 2026⏱ 8 dk okuma👤 Çağlar ÇELİK

Görsel: TechWave tarafından hazırlandı.

Projenizi "son_son_kesin_versiyon2.html" diye adlandırmak, versiyon kontrol değildir. Değişikliği geri alamaz, kimin neyi ne zaman değiştirdiğini göremez ve bozduğunuz kodun iki gün önceki hâlini kurtaramazsınız. Git, bu sorunun standart çözümüdür; GitHub ise onu ekibinize ve dünyaya açan vitrindir.

Bu rehberde sıfırdan başlıyoruz: kurulumdan ilk commit'e, en sık kullanılan 10 komuttan branch ve çakışma çözümüne kadar ilk haftada işinize yarayacak her şey burada.

Git ile GitHub arasındaki fark

İki isim çoğu zaman eşanlımlı kullanılıyor ama farklı şeyler:

GitGitHub
Ne olduğuVersiyon kontrol programı — bilgisayarınızda çalışırGit depolarının barındırıldığı bulut platformu
Çalışma yeriYerel; internet gerekmezÇevrimiçi; hesap ve internet gerektirir
GöreviDeğişiklik geçmişi, dal (branch), birleştirmeYedekleme, iş birliği, kod inceleme, açık kaynak

Kısaca: Git olmadan GitHub işe yaramaz, Git tek başına da yeterlidir — ama yedeklemek ve paylaşmak için GitHub (ya da alternatifi GitLab, Bitbucket) gerekir. Git'in kendisi ücretsizdir ve resmî dokümanı her yerde erişilebilirdir.

Kurulum ve ilk yapılandırma

Kurulum bir kez yapılır. Resmî siteden (git-scm.com) işletim sisteminize uygun paketi indirin; Windows'ta Git Bash programını da kurar. Ardından terminalde kimliğinizi tanımlayın:

  • git config --global user.name "Adınız" — commit'lere yazan isim.
  • git config --global user.email "ornek@eposta.com" — GitHub hesabınızla aynı e-posta olmalı; yoksa commit'ler hesabınıza bağlanmaz.
  • git config --global init.defaultBranch main — yeni depoların varsayılan dalını main yapar; artık master yerine sektör standardı kullanılır.

Yapılandırma git config --list ile kontrol edilir. Bu üç satır, ilk commit'inizden önce atılması gereken adımdır; sonra değiştirmek geçmiş commit'leri düzeltmez.

Temel çalışma döngüsü

Git'in zorlaştığı yer burasıdır; oysa model üç kutudan ibarettir:

  1. Çalışma dizini (working directory): dosyalarınızın düzenlediğiniz gerçek hâli.
  2. Alan (staging area): bir sonraki commit'e ne gireceğini seçtiğiniz bekleme alanı. git add ile oraya taşırırsınız.
  3. Depo (repository): git commit ile anlık görüntü buraya yazılır; artık geri dönülebilir bir kayıttır.

Ve dördüncü adım: git push ile yerel kaydı GitHub'daki uzak depoya göndermek. Bu akışı bir kez kavradıktan sonra gerisi komut ezberi değil, aynı döngünün tekrarıdır. Resmî Pro Git kitabının ilk bölümü bu modeli ayrıntılı anlatır.

İlk deponuzu kurmak: beş komut

Boş bir klasörde ya da mevcut projenizde:

  • git init — klasörü Git deposuna dönüştürür; gizli .git klasörü oluşur.
  • git status — her belirsizlik anında çekilecek ilk komut; neyin değiştiğini, neyin alan dışında olduğunu gösterir.
  • git add . — değişikliklerin tamamını alanına taşır. İleri aşamada tek dosya eklemek için git add dosya.py daha güvenlidir.
  • git commit -m "anlamlı mesaj" — anlık görüntüyü kaydeder.
  • git remote add origin https://github.com/kullanici/proje.git + git push -u origin main — uzak depoyu bağlar ve ilk gönderimi yapar.

Commit mesajı, gelecekteki sizin okuyacağı bir nottur: ne yaptığını (kodu değil) yazın. "düzenleme", "son", "fix" gibi mesajlar bir yıl sonra hiçbir şey ifade etmez.

En sık kullanılan 10 komut

KomutNe yapar
git statusDeğişen, eklenen ve bekleyen dosyaları listeler
git add <dosya>Değişikliği alanına taşır
git commit -m "..."Anlık görüntü oluşturur
git log --onelineGeçmişi tek satır özetler; nerede kaybolduğunuzu bulursunuz
git diffCommit öncesi satır düzeyinde farkı gösterir
git pull origin mainUzak depodaki güncellemeleri indirir — push'tan önce hep
git push origin mainYerel commit'leri GitHub'a gönderir
git branch <ad>Yeni dal oluşturur
git switch <ad>Dal değiştirir (eski checkoutun modern hâli)
git restore <dosya>Commit edilmemiş değişikliği geri alır — geri dönüşü yok, dikkatli olun

Günlük ritim genelde şudur: status → diff → add → commit → pull → push. Bu altı adımı ezberlemek, Git'i "korkutucu" olmaktan çıkarır.

Branch ile çalışmak

Dal (branch), deponun kopyası değil, imlecinizin bulunduğu ayrı bir hattır. Böylece ana daldaki projeyi bozmadan deneme yapabilirsiniz:

  • git switch -c ozellik-ekleme — yeni dal oluşturup oraya geçin.
  • Çalışın, commit'leyin; gerektiğinde git switch main ile ana dala dönüp işinize devam edin.
  • git merge ozellik-ekleme — çalışmayı ana dala birleştirin.

Pratik kural: tek bir iş = tek bir dal = tek bir birleştirme. "Hafta boyunca aynı dala her şeyi yazmak" dalın amacını yok eder. GitHub tarafında dal, Pull Request ile incelendikten sonra birleşir — tek kişilik projelerde bile bu alışkanlık, yanlış commit'leri ana dala ulaşmadan yakalar.

Merge conflict: çakışma nasıl çözülür?

İki dal aynı satırı değiştirdiğinde Git karar veremez ve dosyaya işaretler koyar:

<<<<<<< main
eski sürüm
=======
yeni sürüm
>>>>>>> ozellik-ekleme

Çözüm üç adımdır:

  1. Sakin olun: hiçbir dosya çökmedi; yalnızca iki seçenek arasında seçim bekleniyor.
  2. İşaretli bölgeyi düzenleyin: korunacak metni yazıp <<<, ======= ve >>> satırlarının tamamını silin.
  3. git add + git commit — çakışma çözülmüş sayılır ve geçmişe yazılır.

Çakışma yaşamamak için push'tan önce hep git pull yapın; güncellemeleri erken indirmek, aynı satırı iki kişinin değiştirmesini ciddi ölçüde azaltır. Çözüm gerçekten zorsa git merge --abort ile birleştirmeyi iptal edip dalda çalışmaya devam edebilirsiniz.

İlk haftada yapılan 5 hata

  • Push öncesi pull unutulması: uzak depo sizden ileriyse ret yersiniz. Daima önce pull.
  • Commit edilmemiş işi silmek: git restore ve git clean geri alınamaz. Denemeden önce git status çekin.
  • Hassas bilgiyi commit'lemek: API anahtarı, parola veya .env dosyası bir kez geçmişe girerse silmek zordur. Web geliştirme rehberimizde anlattığımız gibi, gizli anahtarlar kodun parçası değildir; .gitignore listesine ilk günden ekleyin.
  • Çok büyük dosyalar: video, veri seti ve node_modules gibi klasörler depoyu şişirir; GitHub dosya boyutu sınırını aşan push'ları reddeder.
  • Anlamsız commit mesajları: "dosyaları güncelle" yazmak, kod incelemesini ve geri dönüşü imkânsızlaştırır. Mesaj düzeni için Conventional Commits iyi bir başlangıçtır.

Depo düzeni: README, .gitignore ve lisans

GitHub'da ilk izlenim, dosya listesinden önce README'ye bakılarak oluşur. İyi bir README üç soruyu ilk ekranda yanıtlar: bu proje ne yapar, nasıl kurulur, nasıl çalıştırılır. Uzun manifesto değil; tek paragraflık açıklama, üç-beş komut ve varsa bir ekran görüntüsü yeterlidir.

.gitignore ise hata önleme aracıdır: node_modules, .env, derleme çıktıları ve IDE ayar dosyaları ilk commit'ten itibaren listede olmalı. Çoğu dil için hazır şablonlar GitHub'ın depo oluştururken sunduğu seçenekler arasında bulunur; boş bırakmak yerine dilinizi seçin. Açık kaynak yayınlıyorsanız lisans dosyasını da ekleyin — lisans yoksa teknik olarak "herkese açık" ama hukuki olarak "kullanılamaz" demektir. Bu üç dosya, deponuzun en çok okunan parçasıdır ve beş dakikalık bir işten ibarettir.

İlk 30 dakikalık plan

  1. Kurulum + kimlik (5 dk): Git'i indirin, user.name ve user.email tanımlayın.
  2. GitHub'da boş depo (5 dk): Yeni repo oluşturun; README ve .gitignore seçeneğini açın.
  3. Yerelde ilk commit (10 dk): Bir klasöre git init ile başlayın, bir dosya ekleyin, add → commit.
  4. İlk push (5 dk): remote add + push -u origin main. Dosyanın GitHub'da göründüğünü doğrulayın.
  5. Koparıp geri bağlama (5 dk): Bir dosyayı silin, git restore ile geri getirin. Geri dönüşün çalıştığını görünce korku kaybolur.

Merak edilenler

  • İnternet yoksa Git çalışır mı? — Evet. Git yerel çalışır; internet yalnızca push/pull anında gerekir.
  • Her değişikliği commit'lemeli miyim? — Anlamlı her adımı evet. Kural: commit, tek başına anlaşılabilir ve geri alınabilir olmalı.
  • Yanlış commit'i nasıl düzeltirim? — Push edilmediyse git commit --amend; paylaşıldıysa git revert ile geri alma işlemi yapılır — geçmişi silmek yerine üzerine yeni kayıt eklenir.
  • GitHub'a kodum çalınır mı? — Halka açık depolar herkese açıktır. Hassas projelerde özel (private) depo seçin ve erişim anahtarlarını parola yöneticinizde saklayın.
  • GUI mı, terminal mi? — Başlangıçta terminal önerilir; ne yaptığınızı görürsünüz. Sonrasında VS Code'un yerleşik Git paneli veya GitHub Desktop günlük işleri hızlandırır.

Sonuç: geçmiş, projenin sigortasıdır

Git'in gücü tek komutunda değil, her değişikliğin geri dönülebilir bir kayıt olmasındadır. İlk gün beş komut (init, status, add, commit, push), ilk hafta branch ve pull/push disiplini — hepsi bu. Kurulum yarım saat sürer; kurtardığı saatler ise saymakla bitmez.

Bugün tek bir proje klasörü seçin, git init deyin ve ilk commit'inizi atın. Kod yazmaya yapay zekâ araçlarıyla başlıyorsanız bile, o üretilen kodun geçmişini Git tutmadan ilerlemek mümkün değil — versiyon kontrol, AI çağında daha da zorunlu hâle geldi.
